# Трекер КП — техническая справка

Внутренняя система ВПК для учёта заявок на коммерческие предложения: от создания заявки
коммерческим отделом до решения производственного отдела, которое либо считает объём работ
самостоятельно, либо делегирует расчёт одному или нескольким подразделениям.

---

## 1. Архитектура

Один файл `index.html` — HTML + CSS + ванильный JS, без сборки и фреймворков.
Хранение: `localStorage` (кэш) + Supabase REST API (тот же проект, что у «Сервера договоров»,
таблица `storage(key, value)`, ключи разные — коллизий нет). Poll каждые 25 сек.

- `SUPABASE_URL` / `SUPABASE_KEY` — константы вверху `<script>`.
- Пользователи хранятся одним ключом `kptracker_users` (JSON-массив).
- Каждая заявка на КП хранится **отдельным ключом** `kptracker_req_<id>` (по одной записи на
  заявку, как объекты в «Портале объектов») — так правки разных отделов по разным заявкам не
  перетирают друг друга. Список заявок читается через PostgREST-фильтр
  `key=like.kptracker_req_*`.
- Вложения (фото/документы) хранятся так же, как файлы в «Портале объектов»: каждый файл —
  отдельный ключ `kptracker_file_<fileId>`, значение — data-URL (base64). Не подтягиваются
  списком при обычном опросе — грузятся по требованию (`fetchFile`) при клике на вложение.

## 2. Роли и вход

Логины хранятся в `DB.users` (поле `password` — открытым текстом, внутренний инструмент).
Роль определяет, что видно на дашборде/в списке заявок и какие действия доступны в карточке.
Три роли — **базовые, зашиты в код**: `admin`, `commercial`, `production`. Всё остальное —
**подразделения**, динамический список (см. §8): по умолчанию `izyskaniya` (Изыскания) и
`obsledovanie` (Обследование), но admin может добавить любое количество новых прямо из
интерфейса — код их не ограничивает.

| Логин | Роль | Что видит/делает |
|---|---|---|
| `admin` | Администратор | Всё + управление пользователями/подразделениями/менеджерами |
| `kom` | Коммерческий отдел | Создаёт заявки, видит все, финальный результат |
| `pro` | Производственный отдел | Первичный контроль; может оценивать объём работ **сам** (роль `production` — тоже валидный исполнитель, см. §3) и/или делегировать подразделениям; финальное решение |
| `izyskaniya`, `obsledovanie`, … | Подразделения (динамические) | Только свои назначенные заявки на стадии «У подразделений» |

Пароли по умолчанию — `<роль>123` (`admin/admin`). Менять/добавлять пользователей — раздел
«Пользователи» (только `admin`); там же, ниже — управление списком подразделений.

## 3. Жизненный цикл заявки (`stage`)

```
new → subdivisions → decision → accepted | rejected
new → returned                              (первичный контроль = «Нет»)
```

1. **new** — создана коммерческим отделом, ждёт первичного контроля ПО.
2. ПО решает: «Нет» → `returned` (обязателен комментарий — `req.returnReason`, без него кнопка
   не сработает, см. `actionInitialControlReject`); «Да» → выбирает чекбоксами, **кто именно**
   оценивает объём работ по этой заявке → `subdivisions`. Список для выбора — `assessorKeys()`:
   всегда включает `'production'` («Производственный отдел (рассчитать самостоятельно)») плюс
   все текущие подразделения (`divisionKeys()`, §8). Можно отметить только себя (ПО считает само
   и тут же закрывает заявку без единого подразделения), только подразделения (полное
   делегирование), или и то, и другое сразу — комбинации не ограничены. Выбранные получают
   `status:'waiting'`, остальные — `status:'not_involved'` (видно всем, чтобы было понятно, что
   их пропустили осознанно, а не забыли). Список выбранных сохраняется в `req.involvedSubs`.
3. **subdivisions** — каждый вовлечённый исполнитель независимо заполняет форму «Объём
   необходимых ресурсов» → `done`. Подразделения дополнительно могут пометить `insufficient` (с
   комментарием, что нужно уточнить) — этой опции нет у производственного отдела, когда он
   оценивает сам (спрашивать самого себя нет смысла, форма показывается сразу). Если
   `insufficient` — ПО в блоке «Уточнение данных» может написать текстовый комментарий и/или
   приложить файл(ы) (`req.subs[s].clarification`), и только затем «Отправить повторно» (сброс в
   `waiting`); подразделение увидит это уточнение прямо над формой оценки при следующем открытии
   заявки.
   Пока ждём ответа хотя бы от одного вовлечённого исполнителя (`status:'waiting'`), ПО в
   карточке видит явную подсказку «Ожидаем оценку от: …» — так видно, что это нормальное
   ожидание, а не зависшая заявка. Видимость формы оценки в карточке не завязана на список ролей
   — она показывается любому, у кого `req.subs[currentUser.role]` существует и в статусе
   `waiting`, поэтому одинаково работает для `production` и для любого подразделения без
   отдельных условий в коде.
4. Когда все подразделения из `req.involvedSubs` — `done` — заявка **автоматически** переходит в
   `decision`. Если хотя бы одно (но не все) уже `done`, ПО может нажать «Перейти к решению, не
   дожидаясь остальных» (`actionForceDecision`) — досрочно перевести заявку в `decision`, не
   дожидаясь тех, кто ещё не ответил.
5. **decision** — ПО решает: «На переработку» (выбрать из вовлечённых подразделений → возврат в
   `subdivisions`), «Отказ» (обязательное текстовое обоснование → `rejected`), «Берём в работу»
   → `accepted`. При «Отказе»/«Берём в работу» все вовлечённые подразделения, которые ещё не
   ответили (`waiting`/`insufficient`), автоматически помечаются `skipped` — чтобы бейдж не
   выглядел так, будто их оценка всё ещё где-то висит.

Вся история переходов пишется в `req.history[]` (кто, когда, что сделал) и видна в карточке всем
ролям, у кого есть доступ к заявке.

## 4. Структура заявки (`kptracker_req_<id>`)

```js
{
  id, customer, manager, subject, address, amount, workType,
  clientManager,                                     // выбран из DB.managers при создании — см. §7
  govOrder, currency, deadline, advance, tzLink,     // поля из формы «Заявка на КП»; amount/advance — числа (input type=number)
  attachments: [ {id, name, type, size} ],           // фото/документы, содержимое — отдельным ключом kptracker_file_<id>
  stage, createdBy, createdAt,
  returnReason,                                      // обязательный комментарий при stage:'returned'
  involvedSubs: ['production','izyskaniya'],          // кого выбрал ПО при первичном контроле — сам себя и/или подразделения, см. §8
  subs: {                                             // по одному объекту на КАЖДЫЙ ключ из assessorKeys() на момент создания/первичного контроля
    production: {                                     // 'production' — не подразделение, а сам исполнитель-ПО; структура статуса та же
      status:'not_involved'|'waiting'|'insufficient'|'done'|'skipped',
      note,                                            // ответ подразделения: чего не хватает (у production этого поля не бывает — форма без «недостаточно данных»)
      clarification: {text, attachments:[{id,name,type,size}], respondingTo, by, at}, // ответ ПО на note подразделения
      resources:{specialists,laborDays,term,materials,comment}, updatedAt, updatedBy,
      sections: [ {sectionId, name, rate, markupPct, executor, customPrice, days, base, withMarkup} ],  // разделы, заявленные этим исполнителем — см. §10; markupPct — своя наценка/скидка (может быть отрицательной) НА КАЖДЫЙ раздел отдельно; executor — текстовая пометка кто делает; customPrice — если раздел отдан подрядчику/без ставки — своя цена вручную; days — чисто справочное число дней, на стоимость НЕ влияет
    },
    izyskaniya: {...}, obsledovanie: {...}, ...        // + любые добавленные подразделения, см. §8
  },
  decision: { result, by, at } | null,
  rejectionReason: '',
  buildingArea,                                       // площадь объекта, м² — вводится при создании заявки, используется каталогом разделов (см. §10)
  objectType: {id,name,coef} | null,                  // выбирает производственный отдел при оценке, см. §11
  stages: [ {key,name,pct,amount} ] | null,           // доп. стадии (РД/Авторский надзор/Экспертиза), выбирает производственный отдел, см. §11
  finalAmount, kpAddressee, kpOutNum, kpOutDate,      // заполняет КО при формировании КП (см. §5); все суммы — числа
  kpCost, kpMarginPct, kpVatPct,                      // необязательный расчёт себестоимости (см. §5) — только для внутреннего использования
  kpGenerated: {amount, by, at} | undefined,
  history: [ {at, by, action} ],
  customerStatus: 'waiting'|'negotiating'|'discount'|'signed'|'declined', // см. §7
  customerLog: [ {at, by, status, note, amountBefore, amountAfter} ],
  _del                                                 // мягкое удаление
}
```

Поля формы «Объём необходимых ресурсов» (специалисты/трудозатраты/срок/материалы/комментарий) —
дефолт, в исходной заявке этот бланк не был описан отдельно. Меняются в одном месте: блок
`sub-specialists-*` и рядом в `openDetail()` + соответствующие поля в `actionSubSubmit()`.

## 5. Коммерческое предложение (Word) — `generateKp()`

Когда заявка на стадии `accepted`, коммерческий отдел (или admin) видит блок «Коммерческое
предложение для заказчика» с полями: **Кому направляем**, **Исходящий №** (по умолчанию —
`kpNumber(req)`), **Дата письма** (по умолчанию — сегодня), **Итоговая сумма КП** (по умолчанию —
исходная `amount` из заявки, если админ/КО её не менял). Все суммы в приложении — поля
`type="number"` (см. `tonum()`/`fmtMoney()`), а не свободный текст: это защита от того, что кто-то
впишет сумму словами вместо цифр. Итоговую сумму окончательно вписывает КО вручную — оценки
подразделений содержат только объём (специалисты/чел-дни), без цен.

**Необязательный калькулятор** прямо в этом блоке — «Расчёт стоимости»: Себестоимость (₽) →
Наценка/скидка (%, поле принимает и отрицательные значения — `min="-100"`, скидка это просто
отрицательная наценка) → НДС (%, вводится вручную на каждый КП — ставки бывают
льготные/спецрежимные) → кнопка «Подставить в итоговую сумму» (`applyKpCalc()`) считает
`себестоимость × (1+наценка/100) × (1+НДС/100)` и подставляет результат в поле «Итоговая сумма».
Живой пересчёт по мере ввода — `updateKpCalc()`. Себестоимость обычно не вводится вручную, а
подставляется кнопкой «Подставить в себестоимость» из «Итого по разделам» (§10,
`applySectionsTotal()`) — то, что насчитали производство/подразделения по своим разделам,
становится входной себестоимостью ЭТОГО калькулятора, а не сразу итоговой суммой заказчику;
коммерческий отдел уже поверх неё считает свою наценку и НДС. Эти три поля
(`kpCost`/`kpMarginPct`/`kpVatPct`) сохраняются в заявке для
внутреннего учёта маржи, но **в сам документ КП не попадают** — заказчик не должен видеть
себестоимость и наценку компании. Единственное, что просачивается в документ, — ставка НДС: если
она указана, `buildKpBodyXml()` добавляет строку «в т.ч. НДС (X%)» перед «Итоговая стоимость»
(это стандартная практика в российских КП/счетах, ничего конфиденциального не раскрывает).

КП формируется не имитацией, а из **настоящего фирменного бланка** (тот самый
`Фирменный_бланк_ВПК_ПРОГРЕСС_ЭНЕРГО.docx`, который использует компания) — со всеми его
реальными header/footer, логотипом и стилями. Бланк целиком (как zip/OOXML) зашит в код одной
base64-константой `KP_TEMPLATE_DOCX_B64` — тоже «один файл, без сборки», просто сам файл теперь
содержит ещё и шаблон Word, а не только логотип отдельно.

Библиотека **JSZip** (`cdnjs.cloudflare.com/.../jszip/3.10.1/jszip.min.js`, заблокированная
версия) нужна, чтобы открыть этот docx как zip-архив, дописать в `word/document.xml` контент
заявки и пересобрать архив обратно — это единственная внешняя зависимость в проекте, добавлена
осознанно именно для этой задачи (сгенерировать HTML нельзя выдать за подлинный `.docx`).

Кнопка «Сформировать КП (Word)» вызывает `generateKp(id)` (асинхронная):
1. `JSZip.loadAsync(KP_TEMPLATE_DOCX_B64, {base64:true})` — открывает исходный бланк как архив.
2. Читает `word/document.xml`, находит текст **«Генеральный директор»** (это начало готового
   блока подписи в самом бланке) и через `findParaStart()` находит начало **абзаца**, который
   его содержит, чтобы вставить наш контент **перед** ним через `buildKpBodyXml()` — исходящий
   №/дата, «Кому», заголовок КП, одна таблица условий (предмет/адрес/вид работ/гос.заказ/валюта/
   срок/аванс/НДС/итоговая сумма). Сама подпись директора и вся шапка/логотип/стили — из
   оригинального бланка, их код не трогает.
   Раньше здесь была ещё таблица «Состав и объём работ» с разбивкой по подразделениям
   (специалисты/чел-дни/материалы) — убрали намеренно: это внутренние данные планирования
   ресурсов, заказчику их показывать незачем, да и без справочника расценок эта таблица не
   добавляла ничего, кроме визуального шума.
   Взамен, если хотя бы один исполнитель заявил разделы из каталога ставок (§10), в документ
   добавляется таблица **«Состав работ»** — только название раздела и итоговая сумма
   (`sec.withMarkup`), без ставки ₽/м² и без % наценки — это единственные два числа, которые
   заказчик вообще должен увидеть.
3. `wPara/wRun/wTable/...` — маленькие хелперы, собирающие валидный OOXML (`<w:p>`, `<w:tbl>`,
   …) прямо строками — без них пришлось бы тащить полноценную docx-библиотеку.
4. `zip.generateAsync({type:'blob', mimeType:'...wordprocessingml.document'})` — пересобирает
   архив, скачивается как настоящий `.docx`.
5. Только после успешной сборки — сохраняет поля в заявку (`finalAmount`, `kpAddressee`,
   `kpOutNum`, `kpOutDate`, `kpGenerated`) и пишет в историю.

**Три реальных грабли, на которые уже наступали при разработке — не повторять:**
- `findParaStart()` ищет вхождение `<w:p[ >]` (с пробелом или `>` сразу после), а НЕ просто
  `xml.lastIndexOf('<w:p', idx)`. Абзац с подписью в бланке содержит `<w:pPr>` прямо перед
  текстом — простой поиск подстроки `'<w:p'` находит начало `<w:pPr>` вместо начала `<w:p>`,
  из-за чего весь вставляемый контент (параграфы и таблицы) оказывается ВНУТРИ уже существующего
  `<w:p>` — невалидная вложенность, которую Word отказывается открывать («Ошибка Word при
  попытке открытия файла»). При этом XML остаётся well-formed (парсится без ошибок) — эта
  проверка баг не ловит.
- В `<w:pPr>` порядок дочерних элементов жёстко задан схемой: `<w:spacing>` обязан идти раньше
  `<w:jc>` (выравнивание). Переставленные местами — тоже причина отказа открыть файл, тоже не
  ловится проверкой на well-formed XML.
- `<w:tbl>` обязан содержать `<w:tblGrid>` (с нужным числом `<w:gridCol>`) сразу после
  `<w:tblPr>` — без него тоже невалидно.
- Из-за всего этого **для проверки правок в этой функции проверки на `ET.fromstring`
  (well-formed XML) НЕДОСТАТОЧНО** — она проходит даже у сломанного файла. Открывать
  результат через `python-docx` (`docx.Document(path)` + обход `.paragraphs`/`.tables`) —
  это ближе к тому, как парсит документ сам Word, и как раз эта проверка ловит обе проблемы
  выше. Ещё лучше — открыть в реальном Word.
- Контент вставляется не перед абзацем подписи, а сразу после `<w:body>` (правки читаются через
  `/<w:body[^>]*>/`, вставка идёт после конца этого тега), а всё, что было МЕЖДУ началом body и
  абзацем подписи в исходном бланке, — отбрасывается. Это пустые абзацы-заполнители («болванка»
  письма, оставленная для ручного набора текста) — если вставлять перед подписью, не выбрасывая
  их, между шапкой и текстом КП остаётся пустой разрыв на всю оставшуюся часть страницы.

Если бланк компании обновится — просто заменить содержимое константы
`KP_TEMPLATE_DOCX_B64` (взять новый файл, `base64.b64encode` и вставить строкой) и, если
поменяется формулировка/текст подписи, обновить якорь поиска `'Генеральный директор'` в
`generateKp()`. Логотип теперь берётся из самого бланка (в его `word/media/image1.jpg`) — отдельно
хранить его не нужно. `KP_COMPANY` (название/адрес/телефон/ИНН и т.д.) используется только в
тексте вставляемого абзаца «В ответ на ваш запрос … готово выполнить…» — при смене реквизитов
компании поменять там же.

## 6. Ход переговоров с заказчиком — `addCustomerLogEntry()`

После того как КП хотя бы раз сформировано (`req.kpGenerated` существует) и заявка на стадии
`accepted`, в карточке появляется блок «Ход переговоров с заказчиком» — журнал того, что было
**после** отправки КП, отдельно от внутренней истории обработки заявки (`req.history`).

- `req.customerStatus` — один из `waiting` (ожидаем ответ) / `negotiating` (на согласовании) /
  `discount` (просит скидку) / `contract_review` (**договор на согласовании с заказчиком** —
  добавлен 2026-09-10: КП уже согласовано по цене, но сам текст договора ещё утверждается
  юристами/закупкой заказчика — отдельная стадия от торга по цене) / `signed` (договор подписан) /
  `declined` (отказ заказчика). Бейдж с этим статусом виден и в списке заявок, рядом с бейджем
  стадии — можно на глаз оценить, на чём стоят сделки, уже принятые в работу. Дашборд (§7)
  отдельно суммирует `contract_review` и `signed`.
- `req.customerLog[]` — записи `{at, by, status, note, amountBefore?, amountAfter?}`. Добавляет
  коммерческий отдел (или admin) через форму: статус, комментарий и, если сумма поменялась в
  переговорах, — новое значение. Если новая сумма отличается от текущей `req.finalAmount`, в
  запись пишется `amountBefore`/`amountAfter` (видно «было → стало»), и `finalAmount`
  обновляется — это тот же `finalAmount`, что подставляется при повторной генерации КП.
- Это осознанно **не** отдельный этап основного BPMN-процесса (`stage` не меняется) — просто
  журнал поверх уже завершённой внутренней обработки. Никаких обязательных переходов между
  статусами нет, можно добавлять записи в любом порядке.

## 7. Клиентские менеджеры и суммы на дашборде

- **Клиентский менеджер** (`req.clientManager`) — наш внутренний специалист, ведущий сделку;
  отдельно от поля «Менеджер клиента» (это контакт со стороны заказчика). Выбирается при создании
  заявки из простого списка ФИО `DB.managers` (ключ `kptracker_managers`, тот же паттерн
  key→value, что и у `DB.users`) — управляет им admin в разделе «Пользователи» → «Клиентские
  менеджеры» (`createManager()`/`deleteManager()`, мягкое удаление). В самой форме — `<select>` с
  опцией «➕ Добавить нового...» (как список объектов в «Сервере договоров»): выбор `__new__`
  показывает текстовое поле, и при создании заявки новое имя сразу добавляется в общий список.
  Нужен именно управляемый список, а не свободный ввод — иначе "Иванов" и "Иванов И." считались бы
  разными менеджерами при фильтрации/отчётности.
- На странице «Заявки» — выпадающий фильтр по клиентскому менеджеру (`req-manager-filter`,
  `setManagerFilter()`), список имён строится из фактически использованных в заявках
  (`Object.keys` по `clientManager`), не из полного `DB.managers`.
- **Суммы на дашборде** — блок «Суммы» под карточками счётчиков (`dash-money-cards`), виден только
  `admin`/`commercial`/`production` (подразделениям не показываем общие суммы сделок — не их
  зона ответственности). Показывает `fmtMoney()` от суммы `finalAmount||amount` по группам: новые
  заявки, в работе у подразделений, принято в работу, из них на согласовании договора
  (`customerStatus==='contract_review'`), из них подписано (`customerStatus==='signed'`), отказано.
- **Сводная статистика по менеджерам и заказчикам** — отдельная страница «📈 Аналитика»
  (`section-analytics`, пункт `nav-analytics`, виден `admin`/`commercial`/`production` — изначально
  (2026-09-10) таблицы были прямо на странице «Заявки» под фильтрами, но пользователь попросил
  вынести всю аналитику/сводки на отдельный лист, чтобы не загромождать список заявок). Две
  таблицы (`renderGroupStatsRows()`, вызывается из `renderAnalytics()`): по клиентским менеджерам и
  по заказчикам. Считает по **всем** заявкам (`allRequests()`, без привязки к фильтрам страницы
  «Заявки») — кол-во заявок, сумму принятых в работу (`finalAmount||amount` там, где
  `stage==='accepted'`), отдельно кол-во и сумму тех, что `customerStatus==='contract_review'`, и
  тех, что `signed`. Строки сортируются по сумме принятых по убыванию.

## 8. Подразделения — динамические роли

Раньше список исполнителей (МПК/Тула/Кострома/Ростов/ВВ) был захардкожен константой `SUBS`.
Теперь это `DB.divisions` — обычный key→value список в Supabase (ключ `kptracker_divisions`,
тот же паттерн, что `DB.managers`), редактируемый из интерфейса:

- `divisionKeys()` — ключи всех неудалённых подразделений; `assessorKeys()` —
  `['production', ...divisionKeys()]`, то есть «все, кто может быть исполнителем по заявке».
  Практически весь код, который раньше перебирал фиксированный `SUBS`, теперь либо вызывает
  одну из этих функций, либо просто берёт `Object.keys(req.subs)` — ключи, реально
  сохранённые в заявке при её создании/первичном контроле — так добавление нового подразделения
  не требует правок кода нигде.
- `roleName(key)` — универсальное имя роли: сперва проверяет базовые (`admin`/`commercial`/
  `production`), потом ищет `key` в `DB.divisions` (включая уже удалённые — старые заявки,
  ссылающиеся на удалённое подразделение, всё равно показывают его человекочитаемое имя, а не
  сырой ключ). `subLabel()` — то же самое, оставлено как алиас для читаемости в местах, где речь
  именно об исполнителе заявки.
- Управление — раздел «Пользователи» (только `admin`) → блок «Подразделения»: вводится только
  **название** (например, «Изыскания»); ключ для роли генерируется автоматически транслитерацией
  (`translitKey()` + `uniqueDivisionKey()` на случай совпадений) — админу не нужно думать о
  технических идентификаторах. После добавления подразделения его роль сразу появляется в
  выпадающем списке ролей формы «Пользователи» — остаётся создать логин.
- Удаление подразделения (`deleteDivision`) — мягкое: уже существующие заявки, где оно
  участвовало, не меняются (имя по-прежнему резолвится через `roleName`), но выбрать его для
  новых заявок будет нельзя, пока не создать заново.
- SEED-данные при первом запуске на пустой Supabase — `SEED_DIVISIONS` (Изыскания,
  Обследование) и `SEED_USERS` (логины `izyskaniya`/`obsledovanie` с паролями
  `<роль>123`, по аналогии с остальными). Если в Supabase уже что-то лежит под
  `kptracker_users`/`kptracker_divisions`, сиды не применяются повторно (см. `fetchRemote`) —
  их нужно завести вручную через интерфейс, как и было сделано при переходе на эту схему.

## 10. Каталог разделов (ПД + РД, ставки и своя цена)

Справочник, из которого любой исполнитель (производственный отдел или подразделение) может
«заявить» один или несколько разделов при заполнении формы оценки — вместо (или вместе с)
свободного текста в «Объём необходимых ресурсов». Изначально (2026-09-09) заведён только для
**Стадии П** (12 разделов ПП87, реальные ставки из файла заказчика `расчет для стадииП.xlsx`).

**2026-09-10 — редизайн.** Пользователь сначала попросил добавить остальные стадии
(К/ПП/РД/Экспертиза/Авторский надзор) как **% от суммы Стадии П** — это было сделано (см. §11), но
по факту не понравилось для ПД/РД: «если мы выбираем например проектную документацию, там должны
высвечиваться все подразделы, как на Портале объектов». Поэтому каталог `DB.sections` расширен
структурой, скопированной с реальных `STAGE_P`/`STAGE_R` из `Портал объектов/index.html` —
14 разделов ПД + 22 раздела РД (сгруппированных по 5 группам: Общие данные / Архитектура и
конструкции / Инженерные системы и сети (ИОС) / Организация, экология, безопасность / Сметная
документация) — и производственный отдел теперь выбирает не «стадию целиком за %», а конкретные
подразделы нужной стадии, как в Портале. Коэффициенты стадий (§11) остались — но только для
Экспертизы и Авторского надзора, у которых нет естественного деления на подразделы; **важно**: РД
теперь можно посчитать ДВУМЯ способами (% от Стадии П ИЛИ построчно по своим подразделам) — это
осознанно оставлено на усмотрение команды (не блокируется кодом), но использовать оба способа
одновременно на одной заявке даст задвоение стоимости РД — см. «Известные ограничения» (§12).

- **`DB.sections`** — key→value список в Supabase (`kptracker_sections`, тот же паттерн, что
  `DB.divisions`/`DB.managers`): `{id, name, stage, group, rate1, rate2, rate3, _del}`.
  `stage` — `'pd'` (Проектная документация) или `'rd'` (Рабочая документация) — свободная
  строка, не enum: чтобы завести третью стадию, админу достаточно ввести новое значение в поле
  «Стадия» при создании раздела, код ничего не хардкодит (`STAGE_NAME_BY_KEY` — просто подписи
  для двух уже известных значений, для остальных используется само значение `stage`).
  `group` — только для РД, произвольная строка для визуальной группировки в форме (Портал
  использует 5 групп, см. выше) — для ПД не используется. `rate1/2/3` — ставка ₽/м² по тем же
  трём диапазонам площади, что и раньше; **может быть `null` у всех трёх** — это теперь штатный
  случай (изначально почти у всех разделов РД и у двух новых разделов ПД ставок нет), в этом
  случае раздел доступен для выбора, но цену по нему исполнитель вписывает вручную (см. ниже).
  Управление — раздел «Пользователи» → «Разделы работ (каталог ставок)»
  (`createSection()`/`deleteSection()`, мягкое удаление). Редактирование (кнопка «Изменить») —
  `editSection()`/`saveSection()`/`cancelEditSection()`; правки не затрагивают уже сохранённые в
  заявках `req.subs[*].sections[]` — там хранится снимок `rate`/`name` на момент заявления
  раздела, а не ссылка на каталог.
- **`req.buildingArea`** — площадь объекта, м², необязательное поле формы создания заявки.
  `areaTier(area)` возвращает `'rate1'|'rate2'|'rate3'|null`. `sectionHasRate(sec, area)` —
  true только если тир определён И у раздела есть ставка на этот тир; используется везде вместо
  прежней жёсткой привязки блока разделов к наличию площади — **сам список разделов теперь
  показывается всегда** (площадь не обязательна), просто без площади/ставки все разделы становятся
  доступны только со своей ценой.
- **Группировка в форме** — разделы рендерятся не плоским списком, а по стадиям (заголовок
  «Проектная документация (ПД)» / «Рабочая документация (РД)» — порядок и набор берутся из самого
  массива `DB.sections`, не хардкожены), а для РД — ещё и по группам внутри стадии.
- **Выбор раздела** — под каждым выбранным разделом — своя мини-форма (2026-09-10):
  - **Исполнитель** (`.sec-exec-<role>`) — свободный текст, ФИО или название подрядчика,
    чисто информационное поле, на расчёт не влияет.
  - **Подрядчик / своя цена** (`.sec-custom-<role>` + `.sec-customprice-<role>`) — чекбокс,
    при включении подменяет расчёт `rate × buildingArea` на введённую вручную сумму (это цена,
    которую называет внешний подрядчик за раздел целиком); поля «Дней»/«Ставка/день» в этом
    режиме скрываются как неприменимые (`toggleSectionCustom()`). Если у раздела в каталоге нет
    ставки на текущий тир площади (`!sectionHasRate(sec,area)` — так сейчас у всех разделов РД и
    у двух новых разделов ПД), чекбокс-тумблер вообще не рисуется — поле «Своя цена» показывается
    сразу как единственный способ ввести стоимость, обязательный (иначе раздел посчитается
    нулевым).
  - **Дней** (`.sec-days-<role>`) — число дней на раздел, показывается всегда (и на ставочных, и
    на разделах со своей ценой). **Чисто справочное поле** (2026-09-10, было пересмотрено: сначала
    добавили ещё и «Ставка/день, ₽», которая прибавляла `дни×ставка` к стоимости, но пользователь
    попросила добавить дни во все разделы и НЕ прописывать для них стоимость — поле «Ставка/день»
    убрано полностью, `sectionTotal()` дни больше не использует, только `customPrice` или
    `rate(tier)×area`). Нужно для планирования сроков, а не для цены.
  - **Наценка/скидка, %** (`.sec-markup-<role>`) — задаётся **отдельно на каждый раздел**, а не
    одна общая на всего исполнителя, и принимает отрицательные значения (`min="-100"`) — это
    осознанно: при переговорах с заказчиком менеджер часто соглашает скидку не на весь КП, а на
    конкретный раздел, и тогда нужно поменять/обнулить наценку именно там, не трогая остальные.
  Вся эта наценка/подрядчик/дни — внутренние данные, в КП заказчику никогда не попадают (см. §5
  про `withMarkup`-only в таблице «Состав работ»). Формула — `sectionTotal(sec, area, markupPct,
  {customPrice})`: `base = customPrice` ИЛИ `rate(tier)×area`, затем
  `withMarkup = base × (1 + markupPct/100)`. Живой пересчёт — `updateSectionsCalc(role)`.
- **Эксклюзивность** — это единственное жёсткое требование от пользователя по этой фиче: если
  раздел уже заявлен ЛЮБЫМ другим исполнителем этой же заявки, он показывается отключённым
  (`disabled`) с пометкой «уже выбрано другим исполнителем» — `claimedSectionIds(req, excludeRole)`
  собирает id разделов из `req.subs[*].sections` всех ролей, кроме текущей. Проверяется дважды:
  на рендере (какие чекбоксы отключить) и повторно на сервере-стороне-клиента при отправке формы
  (`actionSubSubmit` молча пропускает уже занятый id, даже если чекбокс каким-то образом оказался
  отмечен) — так что даже гонка (двое одновременно открыли форму до того, как второй увидел
  первую заявку) не даёт задвоить раздел.
- **Агрегированный итог** — в блоке «Исполнители» (виден всем ролям с доступом к заявке, как и
  раньше) под списком исполнителей считается сумма `withMarkup` по всем заявленным разделам всех
  исполнителей — «Итого по разделам». Если производственный отдел выбрал тип объекта и/или доп.
  стадии (§11), итог считается как `sectionsGrandTotal × objectType.coef + сумма(req.stages[].
  amount)` — сначала умножается на коэффициент сложности, затем прибавляются доп. стадии (они уже
  посчитаны от той же умноженной базы на момент отправки формы ПО, см. §11). Кнопка «Подставить в
  себестоимость» (`applySectionsTotal`, переименовано и переадресовано 2026-09-10) подставляет
  именно этот полный итог в `#kp-cost` (а не в итоговую сумму заказчику!) — то, что насчитали
  производство/подразделения, становится **себестоимостью** для калькулятора КО (§5), поверх
  которой коммерческий отдел уже накидывает свою наценку и НДС, а не готовой ценой для заказчика.
  Если поле `#kp-cost` сейчас не на экране (например, ПО смотрит на стадии `decision`, до принятия
  в работу) — просто показывает сумму в `alert()` как справочную цифру.
- **В документ КП** — см. §5, таблица «Состав работ»: только название раздела + `withMarkup`,
  без ставки и без %.

## 11. Коэффициенты стадий, категория сложности, тип объекта

Три отдельных множителя/добавки к себестоимости КП, все — внутренние, в документ заказчику не
идут (кроме самих сумм «Состав работ», см. ниже), все — admin-управляемые каталоги того же
key→value паттерна, что `DB.sections`/`DB.divisions`.

**Коэффициенты стадий** (`DB.stageCoefficients`, ключ `kptracker_stage_coefficients`,
`{id,key,name,pct,_del}`) — появились первыми (2026-09-10, до редизайна ПД/РД на подразделы, см.
§10) как способ добавить стоимость доп. стадий проектирования без реального прайс-листа по каждой:
стоимость стадии = `% × себестоимость Стадии П`. После того как ПД/РД получили собственные
подразделы (§10), для НИХ этот механизм избыточен — но для **Экспертизы** и **Авторского надзора**
(у них нет естественного деления на подразделы, это цельные услуги) он остался единственным
способом их учитывать. Сиды: РД=100%, Авторский надзор=2.65% (оба значения — из скриншота
пользователя, реальная практика), Экспертиза — `pct:null` (реальных цифр под рукой не было,
поставлено на усмотрение админа). Управление — «Пользователи» → «Коэффициенты стадий»
(`createStageCoef()`/`editStageCoef()`/`saveStageCoef()`/`deleteStageCoef()`).

**Кто выбирает (2026-09-10, вторая правка):** сначала выбор и применение доп. стадий было в
карточке КП у коммерческого отдела — пользователь поправила: «давай это тоже перенесём в
производственный отдел» (по аналогии с типом объекта, см. ниже). Теперь блок «Доп. стадии
проектирования» — часть формы самооценки **только у `role==='production'`**: чекбокс на каждую
стадию + возможность переопределить % именно на этой заявке, живой пересчёт
(`updateProdStagesCalc()`) считает % не от `kp-cost` (это поле ПО не видит — оно появляется только
в карточке КП на стадии `accepted`), а от **суммы уже выбранных на этой же форме разделов**
(`computeSectionsPickedTotal()`), умноженной на коэффициент типа объекта, если он тоже выбран.
Сохраняется на отправке формы (`actionSubSubmit`) сразу на заявку — `req.stages=[{key,name,pct,
amount}]` (посчитано от суммы **всех** уже поданных на этот момент разделов по всем исполнителям,
не только текущей формы — чтобы не разъехаться с агрегатом в блоке «Исполнители»). В карточке КП
(коммерческий/admin) — только справочный вывод `req.stages`, без возможности изменить. При
генерации КП `req.stages` уходит в `buildKpBodyXml()` — каждая стадия добавляет свою строку в ту
же таблицу «Состав работ», что и разделы (название стадии + сумма, без %).

**Категория сложности (СБЦП 81-2001-25)** — не каталог, а константа `COMPLEXITY_CATEGORIES`
(I/II/III с реальными формулировками из официального текста, п.2.1.5, табл.№6 для обмерных работ
и табл.№7 для обследований — сами расценки в ₽ под рукой не было, только критерии отнесения к
категории). Показывается **только** для `role==='obsledovanie'` в форме оценки — `<select>` +
подсказка с формулировками всех трёх категорий под ним. Сохраняется как
`req.subs.obsledovanie.complexityCategory` (`'I'|'II'|'III'|''`), выводится в общем блоке
«Исполнители» для контекста. Пока чисто информационное поле — на расчёт стоимости не влияет
(числовых коэффициентов по категориям в открытых источниках не нашлось); когда появятся реальные
расценки по категориям, можно будет превратить это в множитель по аналогии с «Тип объекта» ниже.

**Тип объекта / коэффициент сложности** (`DB.objectTypes`, ключ `kptracker_object_types`,
`{id,name,coef,_del}`) — множитель на себестоимость в зависимости от типа объекта; для жилых
домов детализирован по этажности (10 позиций — 1/2/3/4/5/6-10/11-13/14-16/17-20/свыше 20 этажей,
коэффициенты 1.00→1.40, по образцу реального справочника, который показал пользователь) плюс ещё
7 типов объектов (административное здание, общественное здание, торговый объект, промышленное
здание, инженерные сети, объект энергетики, уникальный объект — коэффициенты 1.00–1.50, предложены
мной и подтверждены пользователем). Управление — «Пользователи» → «Тип объекта»
(`createObjectType()`/`editObjectType()`/`saveObjectType()`/`deleteObjectType()`).

**Кто выбирает — важно (2026-09-10, правка после первой версии):** изначально тип объекта выбирал
и применял коммерческий отдел прямо в блоке КП — пользователь поправила: «тип и коэф выбирает
производственный отдел». Теперь `<select id="sub-objtype-production">` — часть формы самооценки
**только у `role==='production'`** (аналогично `sub-complexity-obsledovanie`), сохраняется прямо на
заявку как `req.objectType={id,name,coef}` при отправке формы (`actionSubSubmit`, не привязан к
конкретному заявленному разделу — это атрибут всего объекта, задаётся один раз). Коэффициент
применяется **автоматически**, без отдельной кнопки: в блоке «Исполнители» сумма «Итого по
разделам» умножается на `req.objectType.coef`, и именно эта — уже умноженная — сумма уходит в
`kp-cost` по кнопке «Подставить в себестоимость» (§10). В карточке КП (коммерческий/admin) тип
объекта показывается только для справки, без возможности изменить. В документ КП коэффициент
**не попадает** — это чисто ценовой множитель, как наценка/НДС, заказчику знать о нём не нужно (в
отличие от стадий/разделов, которые реально описывают состав работ).

## 12. Известные ограничения / что доработать при необходимости

- **2026-09-10:** РД можно посчитать двумя параллельными способами — коэффициентом «% от Стадии
  П» (§11) или построчно своими подразделами (§10). Код никак не мешает включить оба на одной
  заявке — это осознанно оставлено на усмотрение команды (гибкость важнее автоматической защиты
  от дублирования), но при формировании КП стоит проверять, не задвоилась ли стоимость РД.
- **2026-09-10:** ставка для площади свыше 1500 м² (`rate3`) пуста у всех разделов Стадии П (как
  и у всех новых разделов ПД/РД, у которых ставок изначально нет вообще) — для таких разделов
  теперь просто обязательна «своя цена» (см. §10), это штатный, а не блокирующий случай.
- **2026-09-10:** категория сложности по СБЦП 81-2001-25 (§11) — пока без реальных расценок в ₽,
  только текст критериев для справки; если появятся официальные цифры по категориям I/II/III,
  стоит завести их как отдельный коэффициент-каталог (по образцу «Тип объекта») и применять к
  себестоимости так же, кнопкой в карточке КП.
- **2026-09-08:** старые фиксированные подразделения (МПК/Тула/Кострома/Ростов/ВВ) полностью
  убраны из кода в пользу динамических (§8); все заявки, созданные до перехода, были удалены
  по прямому указанию пользователя — если когда-нибудь понадобится похожая миграция данных
  «на живую», просто удалением тут не обойтись (пришлось бы писать конвертер `req.subs`).
- Файл ТЗ — только текстовое поле (ссылка/название). Фото/прочие документы — реальная загрузка
  (см. «Вложения» выше), доступна только при создании заявки (менеджером КО).
- Фото сжимаются на клиенте (canvas, макс. сторона 1600px, JPEG q=0.8), прочие файлы — до 8 МБ
  без сжатия. Это ограничение из-за лимита размера тела запроса Supabase/PostgREST.
- Нет хеширования паролей и серверной проверки прав — как и в «Портале объектов», это внутренний
  инструмент за анонимным ключом Supabase.
- Нет истории версий формы ресурсов — при повторном заполнении подразделением старые данные
  перезаписываются (история переходов в `req.history` остаётся).
- Удаление заявки (`deleteRequest`) — мягкое (`_del:true`), данные остаются в Supabase.
- «Клиентский менеджер» выбирается только при создании заявки — сменить его на уже созданной
  заявке пока нельзя (нет формы редактирования, только на этапе `new`).
- Список клиентских менеджеров не связан с логинами/ролями — это просто справочник ФИО для
  атрибуции и фильтра, не отдельные учётные записи с доступом.
- Калькулятор себестоимости не валидирует вменяемость чисел (например, наценка 0% или НДС 0%
  технически допустимы) — предполагается, что коммерческий отдел вводит осмысленные значения.
- **Гонка push/poll:** `pushRequest()` дебаунсит отправку на 500 мс, а фоновый опрос
  (`fetchRemote`, каждые `POLL_MS`=25с) при получении ответа **полностью заменяет**
  `DB.requests` тем, что пришло с сервера. Если опрос выполнится в этом окне 500 мс — до того,
  как локальное изменение реально долетело до Supabase, — свежесозданная/изменённая заявка на
  экране может на миг "потеряться" (перезатрётся более старой серверной копией), пока следующий
  цикл её не подтянет. На практике попадали в это окно только при синтетическом тестировании
  (`createRequest()` сразу же читалось из `DB.requests` без паузы) — не оказалось проблемой в
  реальном использовании, но стоит иметь в виду при написании тестов/скриптов против этого файла.
- **Кэш браузера:** это статический файл, открываемый напрямую (`file://` или локальный сервер) —
  если вкладка была открыта ДО правки `index.html`, она продолжит работать по старому коду в
  памяти, пока её не перезагрузить (F5/Ctrl+F5). Внизу сайдбара есть метка `build YYYY-MM-DD.N` —
  меняйте её при каждой правке и сверяйтесь с пользователем, если что-то ведёт себя «по-старому».
  Особенно опасно смешение старого фронтенда с новыми данными: например, старый код, не знающий
  про `status:'not_involved'`, ждёт `done` от всех 5 подразделений и никогда не переходит в
  `decision`, если реально вовлечены только 2 — выглядит как «пропали действия у ПО».
